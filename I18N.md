# Internationalization

The public church website uses a small static-site i18n runtime (`i18n.js`) rather than a framework migration. It loads one local JSON catalog from `locales/<language>/translation.json`, uses the visitor's ordered `navigator.languages` preferences when no saved choice exists, falls back to English when no supported language matches, and remembers a manual selection in `localStorage` under `imperishable-language`. Changing the selector updates the current page immediately. No translation service is called at runtime.

The selector appears in the public site header and on the splash page. Language names use their native spelling. The runtime updates the document `lang` and `dir`; Arabic uses RTL direction and RTL-specific layout rules. Date, time and number formatting follow the selected locale. Donation currencies remain KES, USD and INR as configured; language selection only changes their presentation format.

## Supported languages

English (`en`), French (`fr`), Kiswahili (`sw`), Hindi (`hi`), Arabic (`ar`), German (`de`), Spanish (`es`), Brazilian Portuguese (`pt`), Simplified Chinese (`zh`) and Japanese (`ja`). The public website currently has no visitor account/profile preference store, so language preference is persisted locally in the browser. The separate external administrator/payment services are not replaced by this change.

## Add a language

1. Add a new language entry to the `LANGUAGES` object in `i18n.js`, with its native name, BCP-47 locale, direction and localized accessibility label.
2. Add the language code to the `supported` list in the early language bootstrap in each public HTML page.
3. Create `locales/<code>/translation.json` by copying the keys from `locales/en/translation.json` and supplying reviewed translations for every source phrase, including runtime/status strings. Keys are the original English text; values are translations.
4. Add `./locales/<code>/translation.json` to the `PRECACHE_FILES` list in `service-worker.js`.
5. Test automatic detection, manual switching, persistence after reload, all public routes and (for RTL locales) layout and form controls.

Keep product names, contact details, personal names and currency codes intact where appropriate. Event content entered by church administrators remains as authored; static interface labels and shipped church copy come from the locale catalogs.
